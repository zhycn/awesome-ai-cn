# 流程：贡献 PR 审阅

## 目的

把一个待合并的条目 PR 按统一清单审到「可合并」状态，守住收录标准与写作纪律。

## 触发

- 新 PR 打开（含贡献者推送新提交后需要复审）
- 维护者说「审一下这个 PR」
- `/review` 指令

## 输入

一个 PR（编号或 diff），或用户描述的条目改动（新增 / 修正 / 状态变更）。

## 角色

- **贡献者**：提 PR 的人（人类或 Agent），按反馈修改
- **审阅者**：执行本流程的 Agent
- **维护者**：拥有合并权限的人，最终决策

## 步骤

### 1. 分诊

看 PR 标题与 diff 规模：

| 情况                             | 处置                                                                       |
| -------------------------------- | -------------------------------------------------------------------------- |
| 单条新增/修正                    | 走第 2 步完整审阅                                                          |
| 结构性改动（加主题/schema/词表） | 转入 `change-management` 流程，要求补 ADR                                  |
| 混合多件事                       | 请贡献者拆成多个 PR（一个 PR 一件事）                                      |
| 明显不满足收录标准               | 用 `templates/issue-replies.md` 的拒绝话术礼貌拒绝，引用 `CONTRIBUTING.md` |

### 2. 完整审阅

执行 `skills/review-entry` 技能的四段清单（收录标准 / 字段合规 / 结构纪律 / 产物一致性），产出「通过 / 需修改 / 拒绝」结论。

### 3. 反馈

- **需修改**：逐条列出问题 + 可直接照抄的修正 JSON，请贡献者更新
- 贡献者推送新提交后回到第 2 步（只核对修改点 + 重跑 `npm run check`）

### 4. 合并后维护动作

由维护者执行（Agent 可提示，不代做）：

- [ ] 按知名度/上手难度调整条目在数组中的位置（顺序是人工编排的）
- [ ] 必要时加 `featured` ⭐（每主题 ≤3，不改变位置）
- [ ] squash 合并，标题即最终提交信息（commitlint 已校验）
- 挪位置/加 featured 的后续提交：维护者直推 main 或开小 PR，不走本流程

## 输出

审阅评论（三态结论 + 问题清单/修正 JSON），落在 PR 上。

## 异常

| 情况                           | 处置                                                                   |
| ------------------------------ | ---------------------------------------------------------------------- |
| 贡献者 14 天无响应             | 建议维护者关闭 PR（评论里给出未完成的修改点）                          |
| force-push 后 diff 全变        | 回到第 2 步全量重审，不接受「只看新增」                                |
| 与 main 冲突                   | 请贡献者 rebase；贡献者不响应则审阅者代 rebase（仅冲突解决，不改内容） |
| CI 红但本地 `npm run check` 绿 | 按 `ci-incident-response` 流程排查环境差异                             |

## 红线

- 校验器通过 ≠ 可合并（口吻、标签纪律靠审阅清单兜底）
- 不因贡献者催促跳过收录标准
- 拒绝时只引用标准，不做主观贬低
- Agent 不合并 PR、不 force push
