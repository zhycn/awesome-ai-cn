# 流程：季度条目时效审计

## 目的

链接巡检只管「打不打得开」；本流程管「还值不值得收」——定期把过时内容降级，保证清单可信度。消费 `.agents/config.json` 的 `limits.staleMonths`（默认 12）。

## 触发

- 每季度初（1/4/7/10 月）维护者发起或维护 Agent 主动提议
- `npm run check` 通过但维护者怀疑内容陈旧时

## 输入

`data/*.json` 全量条目 + 各条目的公开活跃信号（官网更新、仓库提交、发版）。

## 角色

- **维护 Agent**：筛选、逐条核查、起草降级 PR
- **维护者**：确认降级名单、合并

## 步骤

### 1. 筛选候选

候选 = `status` 为 `active` / `beta` 且满足任一：

- `added` 距今超过 staleMonths 且期间无已知活跃信号
- `desc` 里的关键宣称已失效（如「免费」→ 现在收费）
- 所属项目官网内容明显停更（首页公告、最后一篇博客超过 staleMonths）

脚本无现成命令时用 jq/node 临时筛 `added` 日期即可，不需要为此改框架层。

### 2. 逐条核查（抽样优先）

条目多时按主题抽样 20% 起步。对每个候选：访问 `url` 与 `links.repo`（`links` 字段目前尚未在 schema 定义，见 project-map 已知问题；启用前先走 change-management 补 schema），找「最近更新」证据：仓库最近提交、发版记录、官网动态。**拿得到证据才算数**，拿不到证据只进「待人工确认」名单。

### 3. 分类处置

| 证据                               | 处置                                     |
| ---------------------------------- | ---------------------------------------- |
| 明确停维（仓库 archived/官网下线） | PR：`status` → `archived`（不删除）      |
| 仍在维护但宣称过时                 | PR：修 `desc`（走 add-entry 的写作规则） |
| 证据不足                           | 待人工确认名单，交维护者                 |
| 一切正常                           | 跳过                                     |

### 4. 落 PR

批量 PR：`chore: 季度审计——N 条转 archived，M 条修正描述`，引用各条证据链接。跑 `npm run check`。PR 描述注明「季度审计」与核查日期。

### 5. 汇报

一页摘要：核查数、降级数、修正数、待人工确认名单、误判风险说明。

## 输出

降级/修正 PR + 摘要 + 待人工确认名单。

## 异常

| 情况                     | 处置                                              |
| ------------------------ | ------------------------------------------------- |
| 候选量太大（>20%）       | 只报趋势 + 加大抽样，不强推批量降级               |
| 与 link 巡检观察名单重叠 | 优先按 weekly-link-audit 的口径处置，避免双重改动 |
| 维护者对降级有异议       | 回退该条，其余照常；有价值的理由沉淀进 ADR        |

## 红线

- Agent 只**建议**降级，批量 `archived` 必须维护者确认后才合并
- 永不删除条目
- 不凭「感觉过时」降级——只认证据链接
